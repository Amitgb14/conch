# Installation

conch is a single binary for macOS and Linux. Install it with a script, with Go, or from source, and update it later without stopping your agents.

## Install script

macOS and Linux (amd64 and arm64):

```sh
curl -fsSL https://raw.githubusercontent.com/Amitgb14/conch/master/install.sh | sh
```

This downloads the latest release, checks it against the release checksums and installs `~/.local/bin/conch`.

A version as an argument installs that release instead — including an older
one, to go back to it:

```sh
curl -fsSL https://raw.githubusercontent.com/Amitgb14/conch/master/install.sh | sh -s -- 0.2.0
```

| Variable | Effect |
| --- | --- |
| `CONCH_VERSION=0.2.0` | install that release instead of the latest (the argument wins) |
| `CONCH_INSTALL_DIR` | install into another directory |
| `CONCH_RELEASE_URL` | download releases from a mirror instead of GitHub |

Later, `conch update` replaces the binary with the newest release — the same
download, without the script.

## With Go

With Go 1.25 or newer:

```sh
go install github.com/Amitgb14/conch/cmd/conch@latest
```

## From source

```sh
make build        # bin/conch
make test         # go test -race ./...
make release VERSION=0.2.0   # dist/: archives for every platform + checksums.txt
```

Pushing a `v*` tag runs the release workflow, which builds the same archives and publishes them as a GitHub release.

## Updating without stopping agents

The server owns every pane, so a new build takes effect in the server only once it restarts — and a restart would stop the agents. Instead, **reload**:

```sh
conch server reload        # or click the version in the status bar, then r
```

The server execs the new binary in place. It keeps its process ID, so the programs in its panes stay its children; their terminals and the listening socket stay open across the exec; screens, scrollback, terminal modes and agent states are handed over in a state file. Agents never notice — output they write meanwhile waits in the kernel — and the TUI reconnects on its own. Whatever you type into a pane in that moment is held and sent once the pane is back; keys held for more than 15 seconds, or for a pane that didn't survive, are dropped, and the status bar says so.

When the server is older than the TUI, its version shows amber in the status bar. The machine menu has **Reload server** too; a remote machine reloads onto the build `machine upgrade` installed.

<Callout type="warning" title="Servers from before reloading existed">

They need one last `conch server stop`, which stops the server and every pane it owns.

</Callout>

## Auto-update

conch notices newer builds on its own:

- its executable rebuilt or replaced (`make build`, `conch update`);
- a newer GitHub release (checked once a day for release builds; `[update] check_releases = false` turns it off);
- machines running an older build.

The version in the status bar then shows `⬆`; click it for the list and press **u** to update everything:

1. download the release, if there is one, over the conch executable;
2. reload the local server onto it (panes keep running);
3. restart the TUI in place onto the new build;
4. install the build on each ticked remote machine and reload its server.

Remote machines behind your build are listed with checkboxes, all ticked. To update only some, move with `↑` `↓` and press `space` (or click a row) to untick the ones to leave alone; `a` ticks or unticks them all. The box then reads **u update 1 of 2 machines**. Unticked machines stay on their build, also after the TUI restarts; a machine that was offline when you pressed `u` is updated when it connects.

`conch update` does steps 1–2 from a shell, and `conch machine upgrade ID` installs and reloads one machine.

With `[update] auto = true` in [config.toml](/docs/configuration#update), that
daily check installs the release it finds on its own — steps 1–4, without
pressing **u** — and the status bar says so while it runs. It needs
`check_releases`; it is off by default, so the default stays: conch tells you,
you decide.

## Going back to an older version

Every update keeps the binary it replaces (the newest three) in
`$CONCH_HOME/versions` and notes the version it left, so going back is a file
copy, not a download:

```sh
conch update list        # every release published upstream, newest first
conch update rollback    # back to the version before the last update
conch update 0.2.0       # or straight to a version you name
```

`conch update list` marks the running version with `*`, the one
`conch update` would install, and the versions kept locally. Going back notes
the version it leaves in turn, so a second `conch update rollback` comes
forward again.

A version conch never had a copy of is downloaded from its release, exactly
as an update is — so a version that was only ever a local build (`make
build`) can be gone back to only while its kept copy is there. The local
server is reloaded onto the older binary too, so panes keep running; remote
machines follow when you press **u** in the version box or run
`conch machine upgrade ID`.
