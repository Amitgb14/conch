# Sandboxes

A sandbox is a machine in the cloud that conch creates for you, so a long agent task runs away from your laptop and keeps running when you close it. conch makes the sandbox, installs itself there and adds it as a [remote machine](/docs/remote-machines): `-m` and every other machine feature work with it.

In the tree they sit together under **Sandboxes**, one group per provider, so a fleet of them doesn't fill the top:

```
▾ ● local
▾ ● busybox
▾ ▤ Sandboxes            3
  ▾ Daytona              2
    ▸ ● sdx01
    ▸ ○ sdx02   stopped
  ▾ E2B                  1
    ▸ ● sdx01
```

Each one opens like any machine — its projects, agents and terminals underneath — and `m` on its row starts, stops or deletes it. Selecting **Sandboxes**, or one provider, shows what is in it with each sandbox's state. The group appears once there is a sandbox; the same label under two providers is two different sandboxes, and each keeps its own row.

[Daytona](https://www.daytona.io) is the provider conch supports so far.

## Setting up

Create an API key in Daytona's dashboard and put it in your environment:

```sh
export DAYTONA_API_KEY=dtn_…
```

By default conch reads the key from the environment every time and never writes it down — set it where your shell will have it (`~/.zshrc`), and restart conch, since a running process keeps the environment it started with. The key is read by whatever connects: the TUI and the `conch sandbox` commands, never the server, and it never goes over the protocol. A different variable can be named in Settings (`,` → **Sandboxes**) or as `api_key_env` in [`[sandbox.daytona]`](/docs/configuration#sandbox), along with the snapshot, region, auto-stop and what of your environment every new sandbox gets.

If you would rather not keep it in your shell at all, Settings → **Sandboxes** → **API key** takes the key itself. It is then written to `config.toml` (0600) as it is: anything running as you can read it, and it travels with a backup or a synced dotfile, so it is the convenient choice rather than the careful one. A key kept there wins over the variable, the settings show only its last few characters, and emptying the field gives the variable back.

## In the TUI

Press `M`, choose **New sandbox…** and then the provider — Daytona for now, and whatever conch grows later sits beside it; `esc` goes back to the machine menu. The dialog takes a label, a snapshot, a size and the names of environment variables to pass in; leave any of them empty for the defaults. conch creates the sandbox, sets itself up there and adds the machine to the tree, which takes a minute or two. If setting up fails, the sandbox is deleted rather than left to cost, and the reason is shown.

`m` on a sandbox's row adds:

| Item | What it does |
| --- | --- |
| **Start sandbox** | on a stopped sandbox: starts it and connects |
| **Stop sandbox…** | ends its agents and terminals; its files stay. Asks first, saying how many agents are still working |
| **Delete sandbox…** | deletes it and everything in it, and removes the machine. Asks first, listing the branches conch last saw there with commits no remote has, and uncommitted changes |

A stopped sandbox shows `stopped` in the tree, and a spinner while it is starting, stopping or being deleted. **Remove machine** only takes it out of the tree; the sandbox keeps running, and costing, until `conch sandbox rm`.

## Looking at what runs inside

An agent that starts a dev server in a sandbox has nothing to show for it — the port is inside somebody else's machine. `m` → **Open a port in the browser…** asks which port (3000 to begin with, then whatever you used last) and opens a link to it. From a shell: `conch sandbox url ID PORT`, with `-open` to open it and `-expires` to change how long it lasts (an hour by default, a day at most).

The link carries its own credential, so it works in any browser — and so anyone with the link can reach that port until it expires. Daytona keeps 22222, 2280 and 33333 for itself; conch refuses those rather than letting you wonder why the page is wrong.

conch tries the link before opening it. When the proxy reaches the sandbox and finds nothing there — a `502 proxy upstream error` — it says so instead of opening that page, and says what usually mends it: **the server has to listen on `0.0.0.0`, not `127.0.0.1`**. The proxy arrives on the sandbox's own network interface, where a loopback-only server cannot be seen; `next dev --hostname 0.0.0.0`, `vite --host`, `rails s -b 0.0.0.0`. The link is put on your clipboard either way, so you can try it again once the server is up.

## Keeping one to make others from

A sandbox that is set up — the repository cloned, dependencies installed, an agent logged in — can be kept and used as the starting point for the next one. `m` → **Keep a snapshot…**, or `conch sandbox snapshot ID`, names it; `conch sandbox snapshots` lists what is kept and `-rm NAME` forgets one. Then **New sandbox…**, or `conch sandbox create -snapshot NAME`, starts from it.

Daytona takes a cold snapshot, which wants the sandbox stopped first, and says so if it isn't — nothing is changed when it refuses. A snapshot takes a few minutes to become usable, is kept until you forget it, and is charged for storage meanwhile.

## What one has cost

A sandbox costs while it runs, so the tree shows how long each has been up — `4h 12m` beside its row, and the total on the Sandboxes page. Set what an hour costs in Settings → **Sandboxes** → **Price an hour** (per vCPU, per GiB of memory, per GiB of disk, from the provider's own pricing page) and the money appears beside the time: `4h 12m · $0.59`. conch ships no price list, because providers change theirs and a stale one misleads.

**Stopped is not free.** The disk a stopped sandbox keeps is charged until the sandbox is deleted — on a small Daytona sandbox that is most of what it costs over a week. A stopped one therefore reads `disk $0.001/h` rather than nothing, and the Sandboxes page totals it: *stopped ones keep $0.002/h of disk*. It is a rate rather than a total because a provider doesn't say when a sandbox stopped, and a total conch cannot know would be worse than the rate it can.

## Stopping one nobody is using

A sandbox costs while it runs, and it is easy to leave one running. conch pauses a sandbox when no agent there is working, none is waiting for an answer, and no pane has printed for **30 minutes** — Settings → **Sandboxes** → **Stop when idle** changes it (15, 30, 60, 120 or never), per provider, as `idle_stop` in [`[sandbox.<provider>]`](/docs/configuration#sandbox). The status bar says which sandbox went and why, its files are kept, and `m` → **Start sandbox** brings it back where it was.

This is conch's own watching, not the provider's. Daytona's `auto_stop` counts only what reaches it from outside — an ssh connection, a preview request, an API call — so an agent working quietly inside looks idle to it and would be stopped mid-task. conch leaves that timer off and watches the agents and panes it can actually see.

## Starting one again

Stopping a sandbox ends every process in it — that is what stopping means, and the provider keeps the filesystem rather than the memory. The work itself stays: the checkout is as it was, and an agent's conversation is saved in the sandbox's own home.

So conch writes down what was running — each agent, its conversation and its folder, and each terminal — and offers it back when the sandbox starts again:

> sdx1 was running 2 Claude Code agents and a terminal when it stopped. Start them again? 2 agents carry on where they left off.

Each is started in turn, and conch says what came of it: *started 3 of them again in sdx1*, or the reason each one didn't — a sandbox that comes back with nothing showing and nothing said is the thing to avoid. The first pane to start is opened, so it is plain that something is running. An agent whose conversation has gone is started afresh in the same folder rather than skipped; any other refusal is reported instead, so a busy or broken server doesn't quietly get a second agent.

Nothing is started until you say yes: an agent picking up where it left off is not always what you want to happen twice. Settings → **Sandboxes** → **Bring back what was running** turns the whole thing off, per provider (`restore_running`), and then conch keeps no note of what ran — the conversations are still on the sandbox's disk, and the Sessions view still finds them. Agents with a saved conversation are resumed on it; one that saved none starts afresh, and the question says which is which. The note survives conch restarting, and is forgotten when the sandbox is deleted or when something is already running there.

## Deleted somewhere else

A sandbox deleted in Daytona's own interface is gone as far as conch is concerned, however long Daytona takes to finish: `conch sandbox ls` shows it as `gone` rather than sitting at `destroying`, starting or stopping it says so straight away instead of waiting, and the machine it left behind is cleared with `conch sandbox rm ID` (or **Delete sandbox…** in the tree, which then only tidies up). The listing says as much when anything is in that state.

## Commands

```sh
conch sandbox create -label fix-login          # make one, install conch, add it as a machine
conch -m fix-login task -cwd /home/daytona/api "Fix the flaky tests"
conch sandbox ls                               # conch's sandboxes and their state
conch sandbox stop fix-login                   # ends its agents and terminals; files stay
conch sandbox start fix-login
conch sandbox rm fix-login                     # deletes it and everything in it
```

`create` takes `-snapshot`, `-cpu`, `-memory` and `-disk` (GiB), and `-env NAME` to pass one of your environment variables in, say `CLAUDE_CODE_OAUTH_TOKEN`. A named variable that isn't set is refused before anything is created. If setting conch up fails after the sandbox was made, `create` offers to delete it so it doesn't keep costing; `-yes` deletes it without asking.

`start`, `stop` and `rm` take the machine's ID or label, or Daytona's own sandbox ID. `stop` and `rm` ask first; `-y` doesn't. Before deleting a running sandbox, `rm` lists branches there with commits no remote has and uncommitted changes.

`conch sandbox ls` also lists sandboxes conch made that are no longer machines — one whose setting up failed, or one removed with `conch machine rm` — so you can delete them.

## Running until you stop it

Daytona stops an idle sandbox after 15 minutes by default, and an agent working inside doesn't count as activity — only an ssh connection or an API call does. So a sandbox conch creates never stops on its own: close the TUI and its agents carry on. It costs for as long as it runs, so stop or delete it when you're done. `auto_stop` in [`[sandbox.daytona]`](/docs/configuration#sandbox) sets a timeout instead.

conch never starts a stopped sandbox by itself: use **Start sandbox** in its menu, or `conch sandbox start`.

## Getting the work out

The code comes back the way it would from any machine: push the branch from the sandbox, or move the worktree back with **T** (see [Remote machines](/docs/remote-machines)). The sandbox needs its own access to a private repository — a token scoped to that repository, passed with `-env`.

## How conch reaches it

Each connection asks Daytona for a fresh ssh token and goes through Daytona's ssh gateway, so nothing that lets you in is saved. The token is kept out of conch's messages, but ssh has it on its command line while connected, where other users of your computer could see it in the process list. Daytona's gateway key is accepted the first time it is seen.

<Callout type="note">

Daytona keeps the values of `-env` variables with the sandbox. Pass only what the task needs.

</Callout>
