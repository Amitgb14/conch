# Sandboxes

A sandbox is a cloud machine conch makes and adds as a [remote machine](/docs/remote-machines), so a task keeps running with your laptop closed.

<FeatureGrid>
<Feature icon="cloud" title="Make one" href="#in-the-tui">M → New sandbox…, and conch sets it up as a machine.</Feature>
<Feature icon="browser" title="Open a port" href="#looking-at-what-runs-inside">A link to a dev server running inside.</Feature>
<Feature icon="signal" title="What it costs" href="#what-one-has-cost">Time up and what the provider billed, beside each row.</Feature>
<Feature icon="reload" title="Stop and start" href="#stopping-one-nobody-is-using">Idle ones stop; what was running comes back.</Feature>
</FeatureGrid>

In the tree they sit under **Sandboxes**, one group per provider:

```
▾ ● local
▾ ▤ Sandboxes            3
  ▾ Daytona              2
    ▸ ● sdx01
    ▸ ○ sdx02   stopped
  ▾ boat.dev             1
    ▸ ● sdx01
```

## Providers

| Provider | What it is | How conch gets in |
| --- | --- | --- |
| [Daytona](https://www.daytona.io) | sandboxes sized in vCPUs, memory and disk | a fresh ssh token per connection |
| [boat.dev](https://boat.dev) | whole Ubuntu machines in named sizes | your public key, authorized in the sandbox |
| [Devin Cloud](https://docs.devin.ai/cli/cloud) | the VM of a Devin Cloud session | `devin ssh` |

Tensorlake sandboxes are made from the command line only (`conch sandbox -provider tensorlake create`).

## Setting up

Create an API key in the provider's dashboard and put it in your environment, then restart conch:

```sh
export DAYTONA_API_KEY=dtn_…     # Daytona
export BOAT_API_KEY=boat_…       # boat.dev
export DEVIN_API_KEY=cog_…       # Devin Cloud: a service user's key
export TENSORLAKE_API_KEY=tl_…   # Tensorlake
```

Devin Cloud also needs the devin CLI installed (`conch agent install devin`) and signed in (`devin auth login`).

**How:** a different variable, or the key itself, goes in Settings (`,` → **Sandboxes** → the provider) or [`[sandbox.<provider>]`](/docs/configuration#sandbox), with the snapshot, region and auto-stop.

## In the TUI

**How:** press `M`, choose **New sandbox…**, then Daytona (`d`), boat.dev (`b`) or Devin Cloud (`e`). Leave label, snapshot and size empty for the defaults. If setup fails, the sandbox is deleted.

`m` on a sandbox's row adds:

| Item | What it does |
| --- | --- |
| **Start sandbox** | starts a stopped sandbox and connects |
| **Stop sandbox…** | ends its agents and terminals; its files stay |
| **Delete sandbox…** | deletes it and everything in it, after listing unpushed work |

## Looking at what runs inside

**How:** `m` → **Open a port in the browser…**, or `conch sandbox -provider P url ID PORT -open`. Anyone with the link reaches that port until it expires. The server must listen on `0.0.0.0`, not `127.0.0.1`.

## Keeping one to make others from

**How:** `m` → **Keep a snapshot…** or `conch sandbox -provider P snapshot ID`; start from it with **New sandbox…** or `create -snapshot NAME`. Snapshots are charged for storage.

## What one has cost

The tree shows how long each sandbox has been up and what the provider billed: `4h 12m · $0.03` (`~` marks conch's estimate).

**How:** set **Price an hour** in Settings → **Sandboxes** → the provider. `m` → **What it has cost…** or `conch sandbox -provider P usage ID` shows each billed stretch.

## Stopping one nobody is using

conch stops a sandbox when no agent is working or waiting and no pane has printed for **30 minutes**. Its files are kept.

**How:** Settings → **Sandboxes** → the provider → **Stop when idle** (15, 30, 60, 120 or never), or `idle_stop`. conch never starts a stopped sandbox by itself.

## Starting one again

When a stopped sandbox starts, conch offers to start again the agents and terminals that were running.

**How:** say yes when asked. **Bring back what was running** (`restore_running`) turns it off per provider.

## Commands

```sh
conch sandbox -provider daytona create -label fix-login   # make one, install conch, add it as a machine
conch -m fix-login task -cwd /home/daytona/api "Fix the flaky tests"
conch sandbox -provider daytona ls             # conch's sandboxes and their state
conch sandbox stats                            # every provider at once
conch sandbox -provider daytona ssh fix-login  # a shell in it
conch sandbox -provider daytona stop fix-login
conch sandbox -provider daytona start fix-login
conch sandbox -provider daytona rm fix-login
conch sandbox -provider P add ID               # make one ls lists a machine
```

Flags are on [Command line](/docs/cli#sandbox).

## Getting the work out

**How:** `T` on a branch or agent, then **New Daytona sandbox**, moves the worktree there ([Moving a worktree](/docs/remote-machines#moving-a-worktree-to-another-machine)). Bring code back by pushing the branch, or with `T` again.

## The provider registry

Providers others have adapted, such as Hetzner Cloud and DigitalOcean, from [the registry](https://github.com/Amitgb14/conch-sandbox-providers). Install says where your key is sent and which variable it is read from, and asks first; `update` asks again before a file reads your key from another variable or sends it in another header.

**How:** `M` → **New sandbox…** → **\* Install a provider from the registry…**, Settings → Sandboxes → **Add provider…** in Conch.app, or:

```sh
conch sandbox provider search
conch sandbox provider install hetzner
conch sandbox provider update
conch sandbox provider publish NAME    # a pull request through gh
```

## A provider conch doesn't know

An agent reads the provider's API docs and writes a provider file; conch shows each call it will make and checks it before you save. The provider needs ssh.

**How:** `M` → **New sandbox…** → **+ Add a provider conch doesn't know…**, or:

```sh
conch sandbox adapt https://api.example.dev/sandboxes
conch sandbox provider save NAME
```

<Callout type="note">

The provider keeps the values of `-env` variables with the sandbox. Pass only what the task needs.

</Callout>
