# Remote machines

Each machine runs its own conch server, which owns that machine's panes and agents, so work continues there when your laptop sleeps or the network drops. The TUI connects to all of them at once over your normal `ssh`.

## Commands

```sh
conch machine add gpu-box              # an alias from ~/.ssh/config, user@host or ssh://user@host:port
conch machine ls
conch -m gpu-box status                # any command against a machine
conch -m gpu-box new -- make test      # a pane in the machine's home
conch -m gpu-box task -cwd /home/dev/src/api "Fix the flaky tests"
```

With `-m`, `-cwd` is a directory on that machine and must be an absolute path: your shell expands `~` to your own home before conch sees it. Without `-cwd`, `new` and `task` start in the machine's home, outside every project: the task's agent gets the prompt there, with no repository needed. A `-cwd` that isn't a git repository works the same way, in that folder.

No machine of your own? `conch sandbox -provider daytona create` (or `-provider boat`, or `-provider devin` for a Devin Cloud session's VM) makes one in the cloud and adds it here; see [Sandboxes](/docs/sandboxes).

Or press `M` in the TUI. `conch machine rm ID` removes a machine, `conch machine rename ID LABEL` renames it, `conch machine upgrade ID` installs your build there and reloads its server, and `conch machine hosts` lists the hosts in your ssh config. See [Command line](/docs/cli#machine) for flags.

## Adding a machine

<Steps>

<Step title="Probe">

conch probes the machine over ssh (OS, CPU, an installed conch).

</Step>

<Step title="Install">

conch installs itself to `~/.local/bin/conch` there if it is missing or older than your client — `machine add` asks first.

For another platform (say a Linux server from a Mac) conch cross-compiles itself from its source tree (found next to the binary, or `CONCH_SOURCE`) with your Go toolchain, and caches the result in `~/.config/conch/binaries/<os>-<arch>/` until you rebuild conch. A released conch without source or Go downloads the matching release binary instead (checksum-verified). Otherwise put a binary there or point `CONCH_REMOTE_BINARY` at one.

</Step>

<Step title="Connect">

conch connects through `conch bridge`, which starts the server there if needed.

</Step>

</Steps>

## How conch uses ssh

conch runs the system `ssh` with a generated config that includes yours first (so your settings win) and adds keepalives and connection sharing. It stores no secrets; `machines.json` holds only an ID, label and ssh target.

**Connections to other machines are compressed** (`Compression yes` in that generated config). What they mostly carry is panes, and a pane's frame is the whole screen as styled text: one measures 12 KB and deflates to under a kilobyte — ten to sixty times, depending on what is on screen — and 4.3 MB of real frame traffic crossed a LAN here as 54 KB, arriving sooner than it did uncompressed. It is asked for in the config rather than on each command because ssh settles compression when it opens a connection and conch shares connections: a bridge started with `ssh -C` onto a connection some earlier probe had opened gets nothing, and says nothing about it. The same sharing means installs ride along compressed too, which costs little and does a Go binary no harm.

Nothing on this computer is compressed — there is no connection to settle it on, only a unix socket, which moves a frame in about 12 µs where compressing it would take 26 µs. If your machine is as fast as its link (a VM on this host, say), **Settings → Agents → Compress what a machine's panes send** turns it off. It applies to the next conch you start, since the config is written as conch comes up — and then only to connections made after that. ssh settles compression when it opens a connection, and conch keeps one per machine alive for as long as that machine is up, so a connection already open keeps what it was born with: after changing the setting, close it with `ssh -O exit -F ~/.config/conch/ssh/config user@host` and conch redials within a minute. **R** (Reconnect) on its own usually rejoins the same connection, which lingers a minute after its last session.

<Callout type="note" title="Background connections never prompt">

If ssh needs a password, type it in the **Password** field of the `M` dialog. It is handed to ssh only for that add (through a short-lived `SSH_ASKPASS` helper), never saved, and a new host's key is accepted the first time. With **Key login** ticked (the default), conch uses the password once to add your ssh public key to the machine's `~/.ssh/authorized_keys` — your `~/.ssh/id_ed25519`, `id_ecdsa` or `id_rsa`, or a key it creates in `~/.config/conch/ssh` when you have none — and checks that logging in with the key works, so reconnects never need the password. A copy that is dropped part-way is tried again — three attempts, a couple of seconds apart — and a connection that fails with nothing said reads as *the ssh connection failed (255)* rather than a bare exit code. conch's ssh names every key it might use — its own and your defaults — so a machine authorized with one of yours is still let in once conch has made a key of its own, whether or not `ssh-agent` holds anything. If the machine refuses keys, the status bar says so. From a shell, `conch machine add` lets ssh ask for the password on the terminal instead.

To rename a machine, press `r` on it in the tree (or use its menu), or run `conch machine rename ID LABEL`. The ssh target and the machine's ID stay the same.

Machines added or removed with `conch machine add` and `conch machine rm` appear in (or leave) a TUI that is already open within a few seconds; conch watches `machines.json`.

</Callout>

## Machine states

In the sidebar each machine shows its state:

| State | Meaning |
| --- | --- |
| `●` online | connected |
| `⠋` connecting | connecting |
| `○ offline` | unreachable; its last-seen panes stay visible, dimmed, while conch retries with backoff |
| `! setup` | conch needs installing or upgrading — `m` → Install |
| `outdated` | the server there predates your client — `m` → Restart server, which stops its panes |

`R` on a machine reconnects now; `x` removes it. To move a machine onto a new build without stopping its panes, see [Updating without stopping agents](/docs/installation#updating-without-stopping-agents).

**Adding a machine installs conch on it, and that is not optional.** The server there is what owns the ptys: it is why an agent keeps working when you close conch, when the ssh connection drops and when the laptop sleeps, and it is what sessions, git, worktrees, the file explorer and usage are all asking. A machine without it holds no panes at all, so adding one and installing conch are the same act. What it writes is one static binary at `~/.local/bin/conch` (no root, no package manager, `.new` then an atomic rename so a half-copy is never run) and a `~/.config/conch` of its own for the socket, the log and the agent glue — your `~/.claude` and the rest are not touched, since conch launches Claude with `--settings` pointing at its own file. Nothing starts at boot. If what you want is a shell on a machine with nothing installed on it, a [saved SSH host](/docs/interface#ssh-sessions) is the right tool instead: that runs `ssh` in a pane on *this* computer and touches the far side not at all.

**Which build a machine runs.** A machine's page says `conch build …` and then **up to date** or **older build**. The build it names is not the hash of the binary running over there: conch cross-builds that binary from this computer's source, so it is a different file for a different platform and its own hash could never match yours. What the two share is the *source* build stamped into it, which is what the page shows and what conch compares — a machine on exactly your build says so, whatever its own file hash is. Nothing is said about a server too old to report a build, rather than a guess either way. A machine's uptime is not the clue it looks like either: it counts from the *first* server of a chain of reloads, so one upgraded a minute ago still reads as days old, by design — the panes have been alive that whole time. `conch status -m ID` says `(reloaded N ago)` beside it for when the running binary was actually loaded.

## Dropping files on a remote pane

Drag a screenshot or any file from Finder, the desktop or the floating screenshot thumbnail onto conch while a pane on a remote machine has focus. Terminals paste a dropped file's path, which means nothing on the other machine, so conch uploads the file there first and pastes its path there instead. Claude Code attaches a pasted image path as `[Image #1]`; Codex, Gemini CLI and OpenCode take file paths in the prompt.

- The status bar shows `uploading to gpu-box 40% · Shot.png`, then `uploaded to gpu-box · Shot.png`. The path goes to the pane the files were dropped on, even if you moved on meanwhile.
- A paste counts as a drop only when every word in it is the path of a file on this computer, under your home folder, a temporary folder or `/Volumes`. Anything else, and anything pasted into a local pane, is pasted unchanged.
- Files are stored in `~/.config/conch/uploads/<date>/<random>/<name>` on that machine, readable only by you, and deleted after 7 days.
- Files over 25 MB are refused; change the limit, or turn uploads off, in Settings → Agents → Remote machines, or with `[remote]` in [config.toml](/docs/configuration#remote). The server there takes at most 256 MB.
- If one file fails, nothing is pasted and the status bar says why. A machine running an older conch gets the paste unchanged, with a warning to update it.
- SSH sessions under `CLI → SSH` have no conch server on the other side, so drops there paste the local path.

`conch -m gpu-box upload FILE...` does the same from a shell and prints each file's path there.

## Copying files to and from a machine

To put a file somewhere of your choosing, or to bring one back, use the machine's **Files** row (`U` uploads, `D` downloads; see [A machine's own files](/docs/interface#a-machines-own-files)) or the commands:

```sh
conch -m gpu-box upload -to ~/certs ~/doc/ca.pem    # prints /home/you/certs/ca.pem
conch -m gpu-box upload -to ~ ./site                # a folder, copied whole
conch -m gpu-box download -to ~/Downloads ~/logs/run.log ~/results
```

They travel over the connection conch already has to the machine, so they work the same for an ssh host and a sandbox — whose address can change at every start, and which you may hold no key for. Paths there may start with `~`. A name already taken on the receiving side is numbered (`ca 2.pem`) unless `-f` is given, and each path is printed as it lands. Up to 4 GB a file or packed folder; a file dropped on a pane stays limited as above.

### A host you reached with plain ssh

A terminal where you typed `ssh host` needs no conch on that host: `-ssh` names the terminal — its ID or name, as `conch status` shows it — and the copy goes to or from the host it is logged in to, through the host's own sftp server, with the options you typed.

```sh
conch upload -ssh bb ./site ~/doc/ca.pem            # into that host's home
conch upload -ssh p4 -to ~/certs ~/doc/ca.pem       # into a folder there
conch download -ssh bb -to ~/Downloads ~/logs/app.log
```

That needs a key or an ssh agent for the host, since nobody is there to type a password; with `-m`, it is a terminal on that machine. The same host's files are in the terminal's [Files row](/docs/interface#a-machines-own-files).

## Moving a worktree to another machine

When this computer is slow, or you're about to close the lid, move a task to a machine that stays up: `T` on a branch in the tree (or in its changes view, or `m` → **Move to another machine…**), pick the machine, then the project there.

- **Which project:** projects cloned from the same origin come first, however the URL is written (`git@github.com:acme/api.git` and `https://github.com/acme/api` match). If the machine doesn't have it, **Clone … there** clones the origin into the folder you confirm — by default the same place under the home folder as here. The machine needs access to the repository itself; conch never copies keys or credentials.
- **What moves:** the branch's commits, and only those the machine lacks (it compares the branch's history first, so a pushed branch sends none); staged changes arrive staged and unstaged ones unstaged; untracked files, and the project's [local files](/docs/tasks#local-files-in-worktrees) such as `.env`, go along. Files git ignores otherwise — `node_modules`, build output — stay behind. The worktree is recreated there like any conch worktree, under `<repo>.worktrees/`.
- **Agents:** each agent working in the worktree continues there. Its conversation is [handed over](/docs/sessions#on-another-machine) to the same agent in the new worktree (an agent that saved none starts afresh), then its pane here is closed. Terminals stay. An agent in the middle of a task is stopped; changes it makes during the move stay here.
- **This computer:** the worktree and branch are kept, so nothing is lost if something goes wrong; remove them with `x` when you're done.

The status bar follows it: `moving feat to gpu-box · sending 40%`, then `moved feat to gpu-box · 2 agents continue there`. If a step fails, conch shows why in full, nothing changes on this computer, and the other machine undoes what it started. conch refuses when the branch is already checked out there, or has commits there that the moved one doesn't. A worktree with unresolved conflicts, and one whose pack is over 256 MB (large untracked files), can't be moved. Both machines need a conch with this; an older one says to reload it.

## Claude Code on a machine

conch checks whether `claude` is installed on each machine (the machine view shows its version). If it isn't, `c` offers to install it, or press `C` (also in the machine menu, or `conch -m NAME agent install claude`). conch runs Anthropic's official installer (`curl -fsSL https://claude.ai/install.sh | bash`) in a pane you can watch; it installs `~/.local/bin/claude` for your user, no root.

Then `c` starts Claude there: on first run it asks you to log in — open the link it shows on any computer and paste the code back.

<Callout type="note">

conch never copies credentials between machines. For unattended machines Claude also accepts `ANTHROPIC_API_KEY` or a `CLAUDE_CODE_OAUTH_TOKEN` from `claude setup-token`.

</Callout>

Alpine needs `apk add bash curl libgcc libstdc++ ripgrep` (as root) first.
