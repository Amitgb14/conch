# Command line

Everything the TUI does to panes, projects and machines is also a `conch` subcommand, so you can script agents from a shell. `conch help` prints the commands to start with, and `conch help all` every one.

## Help

```sh
conch help               # the commands to start with
conch help all           # every command
conch help branch        # one command: what it does, how it goes, examples
conch branch -h          # the same (--help too)
conch branch pr -h       # a subcommand's own flags
```

`-h` right after a command is answered before the command runs, so `conch status -h` explains `status` rather than starting a server to report on. A mistyped command gets the one it probably was — `conch brnach` says *did you mean conch branch?* — and exits 2, as any unknown command does.

An error says what to do next, as `conch doctor` does: with no server running, a command says so and that `conch` starts it (`conch server stop` says there is nothing to stop); a pane or project that is not there names the command that lists them (`conch status`, `conch project ls`); a word that is not a subcommand gets the one it was likely meant to be and `conch CMD -h`; a usage line ends with `conch CMD -h explains it`; and `-m` with a name conch has no machine by says it was tried as an ssh host. The server's generic `bad_request:` and `internal:` codes are left off what is printed; the ones a script or an agent reads — `out_of_scope:`, `not_found:` and the rest — stay.

## Scripting

```sh
conch task -cwd ~/src/api "Add a health check endpoint"   # pane, worktree, branch
conch new -agent claude -cwd ~/src/api                   # Claude in the repo
conch send p1 "fix the failing tests" && conch send -keys p1 enter
conch read p1                          # visible screen as text
conch status                           # panes with agent state
conch project ls                       # projects, base, worktrees
conch branch commit -m "Fix the flaky test" && conch branch pr   # finish a task
conch worktree clean -y                # remove finished worktrees and their branches
conch wait p1 && conch send p2 "review what p1 just changed"   # chain tasks
conch agent prompt -wait p2 "check finding 3 again" && conch read p2   # one agent driving another
conch close p1
conch server reload                    # run a new build; panes keep running
conch server stop                      # stops the server and all panes
```

<Callout type="warning">

`conch server stop` stops the server **and every pane it owns**. To move onto a new build, use `conch server reload`.

</Callout>

On macOS the server runs with `GODEBUG=asyncpreemptoff=1`, restarting itself once at start-up to get there: a reload re-execs the server process, and macOS makes that wait for scheduling signals a busy server never takes, which would leave it serving nothing. If a reload ever leaves the socket in place with nothing serving it, `conch status` says the server is *not answering* rather than that it is gone, and simply running `conch` again clears that socket and starts a fresh server. The panes of the old one are lost; nothing else needs cleaning up by hand.

## Global flag

`-m MACHINE` (or `--machine MACHINE`) before the subcommand runs it against a [remote machine](/docs/remote-machines) instead of this one; `local` means this machine.

```sh
conch -m gpu-box status
```

## Subcommands

### conch

`conch` with no subcommand opens the TUI, starting the server if needed.

Inside one of its own panes it refuses, the way tmux refuses a nested session: the inner TUI would take the keys and the mouse, and closing the pane would kill it. Detach with `ctrl+b d` first, or run `CONCH_PANE_ID= conch` to open one inside the pane anyway (`conch -m MACHINE` for another machine's TUI always works).

### server

| Command | Description |
| --- | --- |
| `conch server` | run the server in the foreground |
| `conch server stop` | stop the server and every pane it owns |
| `conch server reload [-binary PATH]` | run a new conch build without stopping panes; `-binary` picks the program to reload into (default: the server's own executable path) |

### Pane names

Every command that takes a pane's ID — `send`, `read`, `close`, `redraw`, `wait`, `rename`, `agent explain`, `agent prompt` — takes its name as well: the one in `conch status`'s name column, set with `conch rename` or `conch task -name`. That is how one agent addresses another it started, without keeping track of IDs:

```sh
conch task -name reviewer -agent codex "Review the diff on this branch"
conch agent prompt -wait reviewer "Check finding 3 again" && conch read reviewer
```

- An ID is always an ID: `p` and a number is never looked up as a name, so names of that shape are refused.
- A pane on another machine can be named `MACHINE:ID` — `conch read busybox:p3` is `conch -m busybox read p3`. That is how the TUI's status bar, Conch.app and the phone show a pane's ID, and what their **Copy pane ID** gives, so a copied ID works as it is. The machine is its ID, its label or its ssh target, as `-m` takes, looked up in that order — so an ID always reaches its own machine — and the windows name a machine by its label only when no other machine answers to it, else by its ID. One that is not in `conch machine ls` is left alone, and a ref that disagrees with `-m` is refused. Only the command's pane is read this way: `conch send p5 look at busybox:p3` sends that text as it is.
- A name is looked up once, when the command starts; a `wait` then stays with that pane.
- Names are exact and case sensitive. A name two running panes share is refused rather than guessed — say which with its ID. A pane that has ended still answers to its name until another running pane takes it.
- Names belong to one machine's server, so `-m` looks them up there.

### machine

`conch machine bridge ID` carries conch's protocol to that machine's server on its own stdin and stdout, reached the way conch reaches it — its ssh options, a sandbox's gateway — by running `conch bridge` there. It is how the [Mac app](/docs/mac-app) talks to a machine other than this one, and anything else that speaks the [protocol](/docs/protocol) can use it the same way. It installs nothing: a machine without conch, or with one too old for this build, is said, with `conch machine upgrade ID` to fix it.

### attach

```sh
conch attach p3               # show pane p3 here and type into it
conch attach -hold p3         # and keep its last screen when it ends, until a key
conch attach -raw p3          # give this terminal the program's own output to draw
conch -m busybox attach p3    # one on another machine
```

`conch attach` puts one pane in the terminal it runs in: the screen conch keeps for that pane, redrawn as it changes, with what you type, the mouse and the window's size going back to it. It is how the [Mac app](/docs/mac-app) shows a pane in a view of its own, and it works in any terminal. The pane's program never sees this terminal — conch's server is its terminal — so arrows and the like are passed by name for the server to send the way the program asked, and the mouse only reaches a program that asked for it. The wheel follows the TUI's rule: on the main screen it scrolls conch's history, on the alternate screen it goes to the program. Shift with Page Up and Page Down scrolls the history a page at a time, and shift with Home and End goes to its oldest line and back to the live screen; a full-screen program gets those keys instead. Closing the terminal detaches and the pane keeps running; when the pane ends, `attach` ends too and says how.

With `-raw` the terminal gets what the program wrote rather than conch's screen of it, so it draws the pane itself: its own scrollback, selection, search, images and cursor shapes. This is how the Mac app's Ghostty shows a pane. It starts with output that rebuilds the history and screen, then follows the program as it writes. The questions conch already answers for the program — where the cursor is, what the terminal is, its colours — are taken out, so the program is not answered twice; the ones only this terminal can answer, such as whether it draws images, still reach it. The pane's size is still settled by the server between everyone showing it: this terminal draws the output at the pane's size, and typing here makes it this terminal's. Its own answers and the pointer just moving take nothing. `-view` (with `-raw`) only looks: it never resizes the pane or takes its size. Against a server too old for it, `-raw` is the plain attach.

### When an agent runs these commands

An agent in a conch pane can drive conch with the same commands — start a reviewer, prompt it, read its answer. `conch agent skill -apply` teaches it how, and when to stop and ask you; [Agents working together](/docs/agents-together) walks through it with examples. What it may *change* is kept to its own work:

- **panes it started**, and the panes those started, in any project;
- **panes in its own project**, whoever started them;
- **its own project's** branches and worktrees.

Anything else — typing into, closing, renaming or marking as seen another project's pane, sending it keys or a broadcast, removing another project, committing, pushing or discarding there — is refused with `out_of_scope`, and so is `conch server stop` or `reload`, and changing your own setup: the agents' skill, the library, a sync, or which local files a project copies into its worktrees:

```text
conch: out_of_scope: the claude agent in p4 may not close p1: it did not start it, and it is in another project; do it from the TUI or a terminal pane
```

Reading is never refused (`read`, `status`, `wait`, sessions), and neither is starting panes and tasks: what an agent starts is its own, and each pane in the server's pane list carries who started it (`created_by`).

conch tells who is asking from the operating system — the process at the other end of the socket, and its parents up to a pane — not from `CONCH_PANE_ID`, so unsetting that changes nothing. Only a pane with an agent running in it is held to this: a terminal pane, the TUI and scripts outside conch act as you. It is a guard against a confused agent closing the wrong session, not a sandbox: a program set on escaping can leave the pane's process tree.

**On other machines.** `-m` from an agent's pane carries its scope along: conch asks this machine's server who is running the command and, for an agent, has the other machine's server hold the connection to what that agent started there — its panes (and theirs), and the projects it started them in. It has no project there otherwise, so another project's panes stay out of reach even when they share a name with its own. A machine whose conch predates this isn't driven from an agent's pane at all; `conch machine upgrade` it. A terminal pane's `-m` is you, as before. Like the rest, this asks conch: an agent that runs `ssh` itself, or points `CONCH_SOCKET` elsewhere so this machine's server can't be asked, is not held by it.

| --- | --- |
| `conch agent explain ID` | show how a pane's agent state was decided, as JSON |

### task

`conch task [-cwd DIR] [-branch B] [-base B] [-agent NAME] [-n N] [-name N] [-at TIME] [-every SPAN] [-queue [-wip N]] [-after REF] PROMPT` creates a branch and worktree and starts an agent with the prompt (`-at` later, `-every` again and again, `-queue` when the project has room, `-after` once other work has finished, on top of it: see [Later, and on a schedule](/docs/tasks#later-and-on-a-schedule); `conch schedule` lists and removes what is scheduled); in a folder that isn't a git repository — or, with `-m` and no `-cwd`, the machine's home — the agent works there with no branch. See [Tasks](/docs/tasks).

| Flag | Default |
| --- | --- |
| `-cwd DIR` | a directory in the project; default: the current one. With `-m` it is required, as an absolute path on that machine |
| `-branch B` | branch name; default: derived from the prompt |
| `-base B` | branch to start from; default: the project's base |
| `-agent NAME` | `claude`, `codex`, `gemini` or `opencode`, or several separated by commas; default: `[agents] default`, and with none chosen Claude Code — or, on a machine last found without it, an agent it has (the server knows once anything has asked: opening conch, `conch doctor` or `conch agent status`). An agent this machine is known not to have is refused with how to install it, rather than started to die with *command not found*; after one dies that way, a task naming no agent looks for the others — and from that look on, the missing one is refused by name |
| `-n N` | attempts at the same prompt, each on its own branch (default: one per agent, at most 10) |
| `-name N` | name the task's pane, to address it by in place of its ID (see [Pane names](#pane-names)). Refused while a running pane has that name, and with more than one attempt |

### branch

Finishing a task from a script, the same steps as the [changes view](/docs/tasks#finishing-a-task). Every command takes `-cwd DIR` (a directory in the project; default: the current one) and `-branch B`; without `-branch` conch uses the branch checked out in that directory. With `-m MACHINE`, `-cwd` is required and must be an absolute path on that machine.

| Command | Description |
| --- | --- |
| `conch branch commit -m MESSAGE [-file PATH]...` | commit every change on the branch, or only the `-file` paths (repeat the flag; a rename needs both its paths). Prints the new commit |
| `conch branch push` | push the branch, setting its upstream on `origin` (or the only remote) the first time; a remote that has moved on refuses it, and `-rebase` takes its commits, puts the branch's own on top and pushes |
| `conch branch pr [-title T] [-body B] [-draft]` | push, then open a pull request into the base with `gh`, and print its URL. Without `-title`, gh fills the title and body from the commits |
| `conch branch merge [-no-squash] [-m MESSAGE]` | merge the branch into the base where the base is checked out, squashed unless `-no-squash`. A merge that conflicts is undone and the command fails |
| `conch branch discard [-n] [-force]` | remove the branch's worktree and delete the branch. It refuses when that would lose uncommitted files or unpushed commits, unless `-force`; `-n` only prints what would go |
| `conch branch fix-ci [-agent A]` | send the branch's newest failed CI run — its log's end and a link to it — to the agent working on the branch, as `f` in the review queue; with none there, start one (`-agent`, else `[agents] default`) in the branch's worktree with it. Refused while that agent waits on a question of its own |

```sh
conch branch commit -m "Add the health check" && conch branch pr -title "Health check"
conch branch merge && conch branch discard      # land it and clean up
```

### review

The [changes view's comments](/docs/interface#changes-view) from a shell: the same ones, kept by the server, so a comment written here shows on `a`'s hunk marks and the phone's agent card, and the other way round. Like `branch`, every command takes `-cwd DIR` and `-branch B`, and without `-branch` uses the branch checked out in that directory.

| Command | Description |
| --- | --- |
| `conch review` | list the comments waiting for the branch's agent, oldest first, each with its ID, where it is and who wrote it when an agent did. The unresolved comments on the branch's pull request follow, with the reviewer (`alice on GitHub`), their replies and their link |
| `conch review add FILE[:LINE] NOTE` | comment on a file, or one line of it (`a.go:12`). Every word after the file is the note. Run from an agent's pane, the comment says which agent wrote it |
| `conch review rm ID` | take a comment away. A pull request's comment is refused: answer or resolve it on GitHub |
| `conch review reply ID ANSWER` | answer a comment, by its id — what an agent that was sent it does once it has dealt with it: what it changed, or why it left it. The answer shows under the comment's line in Conch.app, signed by the agent. Answered by a person, the comment waits to be sent again with its thread. Not a pull request's: answer those on GitHub. Needs `review.thread.v1` |
| `conch review send [-agent A]` | hand every comment waiting to the agent working on the branch as one message, numbered, each of conch's own with its id; they are marked as sent to that agent (a server before `review.thread.v1` clears them). The pull request's comments stay on GitHub but aren't sent again until somebody replies to them. Refused while that agent waits on a question. With no agent on the branch it is refused too, unless `-agent` names one to start in the branch's worktree with them |

```sh
conch review add api/login.py:42 "This swallows the timeout; let it raise."
conch review send
```

An agent [kept to its own work](#when-an-agent-runs-these-commands) may comment on and send for its own project's branches, and no others — which is what lets a reviewer you started leave its findings as comments instead of a file.

### relay

```sh
conch relay [-listen ADDR] [-cert FILE -key FILE]           # a relay phones and conch webs meet at
```

`conch relay` runs a [relay](/docs/phone#through-a-relay) on a server of your own (`:8443` by default): `conch web` connects out to it, a phone opens its address, and it copies the encrypted session between them without being able to read it. It stores nothing and serves the phone's app — which is why it should be a server of your own: a relay that served a changed app could read what the phone sees. Without `-cert`, put a proxy that does HTTPS in front of it — a phone's browser encrypts only on an https page.

### cloud

```sh
conch cloud agent [-boot FILE] [-state DIR] [-user NAME]   # inside a Conch Cloud machine only
conch cloud install [-user NAME]                          # ready a machine image (as root)
conch cloud git-credential [-socket PATH] get              # git's credential helper there
```

`conch cloud agent` is the machine's side of Conch Cloud, and runs **inside** a cloud machine: its host starts it (the `conch-cloud-agent` systemd unit — see [Cloud machine image](/docs/cloud-machine)) after writing `/run/conch-cloud/boot.json`. It refuses a `boot.json` anyone but its owner can read, keeps the machine's Noise key in `/var/lib/conch/cloud/noise.key` (0600, made once), starts the machine's conch server as `-user` (`conch` when it runs as root), says hello to the control plane, reports what the agents are doing so an idle machine sleeps, and joins the relay as the room's gateway so clients reach the server through an end-to-end encrypted tunnel. Agents it starts are given the account's env secrets (a shell is not, and only the server it registered with may ask for them); the machine token and those secrets are never written to disk, though a running agent's environment, and the token git is handed, are readable by processes of the same user — see [Cloud machine image](/docs/cloud-machine). It exits 3 when the control plane refuses its token — each inject gives the machine a new one and restarts the agent — and 4 when the control plane refuses the machine itself. `install` readies a machine image: it writes the `conch-cloud-agent` unit (running this conch), enables it and makes `/var/lib/conch/cloud`; the user (`conch` by default) must exist. `git-credential` is what git asks for the git proxy's password: the machine token, from the agent's memory.

### mcp

```sh
conch mcp                                                   # an MCP server on stdin and stdout
```

An agent that would rather call a tool than a command talks to conch through `conch mcp`: a [Model Context Protocol](https://modelcontextprotocol.io) server over stdio, in front of the same socket the CLI uses. A tool call comes back as a typed result and a refusal it can act on, where shelling out hands it a screenful of text to parse.

| Tool | What it does |
| --- | --- |
| `list` | the panes you may see, each with what its agent is doing and the [subagents](/docs/agents-together#claudes-own-subagents) running inside it |
| `read` | a pane's screen now (`tail` for its last lines — leave it out for an agent, whose last lines are its prompt box) |
| `start` | an agent in a pane of its own, in a folder that exists |
| `prompt` | an agent's next message; `wait` holds until the work it starts has ended |
| `wait` | block until a pane's agent is `done`, `idle`, `waiting` or `working` |
| `task` | a branch, a worktree and an agent on a prompt |
| `rename` | name a pane, to address it by that instead of its id |
| `view` | what the person is looking at: the tabs, what is in each, and which pane has the keyboard |
| `show` | ask the terminal to put panes in front of them — one is revealed, several open side by side in a tab of their own |

`view` and `show` are the two that reach past the server to the screen. The server owns panes and the terminal owns the arrangement of them, so conch carries both ways: a TUI publishes what it is showing, and a `show` is passed back to it as a request. A request, not an order — the panes asked for are **gathered side by side in one tab** and nothing else is touched. They move rather than being copied, since a pane is shown in exactly one place, which is the same rule that governs `ctrl+b !` and dragging a pane between tabs. An agent may only show panes it could already type into, by the same scope that governs `prompt`.

The tools are the same work as [`conch agent prompt`](#agent), `conch wait`, `conch task` and the rest — the same server methods with the same payloads — so the two doors cannot drift. Scope comes for free: conch finds the caller from the socket's peer pid walked up to a pane's program, so an MCP server an agent starts inside its own pane reaches only [what that pane may reach](/docs/agents-together#what-an-agent-may-do), and nothing in a tool call can widen it.

Installing it is one action, because the entry is the same for every agent — the [library](/docs/tasks#shared-mcp-servers-and-skills) writes it in each one's own format:

```sh
conch agent library mcp          # conch's own tools, as a server in the library
conch agent library apply        # write it into each agent's configuration
```

Or in the TUI: `,` → **Agents** → **Shared MCP servers & skills…** → **Add conch's own tools…**, then **Apply…**. It is `conch mcp` on stdio with nothing in its environment — it finds its socket the way every other command does — and the command is the bare name, so an update that moves the binary doesn't strand it. Adding it twice is adding it once. Restart an agent afterwards for its client to list the tools.

[Three reviewers at once](/docs/agents-together#three-reviewers-at-once) is what this is for: several helpers, several kinds of agent, no shell.

Stdin and stdout are the protocol: notes go to stderr, one request per line (this revision of MCP has no batches), answered one at a time in order, and a `wait` tool holds the session until it ends, as `conch wait` holds a shell. A tool that names a pane refuses a name shaped like a pane id or one another running pane holds, as `conch rename` does — ids win, so such a name would pick out nothing. `timeout_seconds` defaults to 1800, 0 waits with no limit, and anything over a day is capped.

### completion

```sh
eval "$(conch completion zsh)"     # in ~/.zshrc, after compinit
eval "$(conch completion bash)"    # in ~/.bashrc
conch completion fish > ~/.config/fish/completions/conch.fish
```

Tab then completes commands and their subcommands, and what is running now: pane ids and names for `read`, `send`, `wait`, `close`, `rename`, `redraw`, `show` and `agent prompt`/`explain`; machines after `-m` and for `machine rm`; hosts from your ssh config for `machine add`; projects for `project rm`; agents for `agent install` and `-agent` (also a comma list, `-agent claude,co<tab>`); providers for `sandbox -provider`. zsh and fish show what each one is beside it — the commands with what they do, a pane with its agent, folder and state — so `conch <tab>` is also a way to find out what conch can do.

The scripts are a few lines that ask `conch` itself on every tab, so a pane started a second ago completes, and an update brings new commands with it. Panes and projects come from the local server: it is never started for a tab, and one that does not answer within a second and a half gives nothing rather than a hung prompt. Another machine's panes (`-m NAME read <tab>`) are not asked for, since that is an ssh connection away. Where conch has nothing to offer, the shell completes file names. `conch completion` with no shell says how to turn it on for the one you use. [Homebrew](/docs/installation#with-homebrew) installs it for all three.

### app

```sh
conch app                      # open conch in a terminal of its own
conch app -terminal kitty      # in that one
conch app ls                   # which terminals conch can open here
conch app install              # put conch in the desktop's applications, with its icon
conch app remove               # take it out again
```

conch is a terminal program, so it is usually started by typing into a terminal somebody set up first. `conch app` starts the terminal as well: it writes a configuration of its own and opens a known terminal with **only** that one, so a terminal that was never configured — or configured years ago for something else — stops being conch's problem. The terminals it knows, in the order it picks one: **ghostty**, **kitty**, **foot**, **alacritty**. It looks for each on your `PATH`, then in the places a terminal lives that the `PATH` in hand may not have — `/usr/local/bin`, `/usr/bin`, `~/.local/bin`, `/snap/bin` and the flatpak export directories on Linux, Homebrew's on macOS — and on macOS in `~/Applications` and `/Applications`, where a terminal is an application and not a program on `PATH` at all. Both detours matter: ghostty adds its own directory to `PATH` only for the shells *it* starts, so a shell from a conch pane or launchd cannot see it; and a desktop entry is started with the session's `PATH` rather than your shell's, so a terminal in `~/.local/bin` could be found when you type `conch app` and missed when you click the icon — which, with `Terminal=false`, would show nothing at all. `conch app ls` says which it found and where. Each is started in the way that leaves your own config unread (`--config-default-files=false`, `--config`, `-c`, `--config-file`), which is the whole of the trick.

Terminal defaults are good; what conch needs is that nothing broken is read on top of them. Beside what makes the window conch's own (below), the only settings in the file are the ones that would otherwise bite: `TERM` held at `xterm-256color` when nothing the window could read describes the terminal's own entry (the thing [`conch doctor`](#doctor) warns about) — asked of this computer *and* of the terminal itself, since one may carry its own terminfo and point `TERMINFO` at it for what it starts, as macOS Ghostty does from inside its bundle; asking only the environment conch happens to be in cost the window `xterm-ghostty` for no reason, and, for ghostty, single-instance turned off and quit-after-last-window-closed turned on. Both of those are about the window being conch's: a ghostty already running would otherwise make it itself, from its own configuration rather than conch's, and on macOS — where ghostty cannot be started from the command line at all, so conch goes through `open -na Ghostty.app --args` — the separate instance that creates would sit in the Dock with nothing in it after the conch window was closed, one more for every launch. Anything you want to add goes in `<name>.local.<ext>` beside it (`~/.config/conch/app/ghostty.local.conf`), which is included when it exists; the generated file itself is rewritten every time, so edits there are lost.

`conch app install` puts conch in the launcher: a `conch.desktop` entry and conch's own icon under `~/.local/share` on Linux (`$XDG_DATA_HOME` when set), or a `conch.app` bundle in `~/Applications` on macOS, where the icon is built from conch's with `sips` and `iconutil` and left out if they are missing. Both are files of your own, nothing is installed system-wide, each path is printed as it is written, and `conch app remove` takes exactly those away. Neither touches a file conch did not write: on a Mac's usual case-insensitive disk `~/Applications/conch.app` is the same name as [Conch.app](/docs/mac-app), so a bundle there whose identifier is not the launcher's (`dev.conch.app`) — the native app, or anything conch cannot read as its own — is left as it is, and install and remove say so; keep Conch.app in `/Applications` to have both. On Linux an entry or icon by the same name that conch did not write is left alone the same way. It refuses to install when none of the terminals is there, since the entry would be a launcher that does nothing when clicked.

The window is conch's in a few more ways, all of them settings of the terminal rather than anything drawn around conch:

- **The theme.** Its background, text, cursor and selection are the [theme](/docs/interface#settings) in `config.toml` (`[ui] theme`, `accent`), so the window is that theme rather than a terminal's stock black with conch's colours on it. A theme changed in Settings reaches the window the next time `conch app` opens one.
- **⌘ shortcuts** (Ghostty and kitty). `⌘T`, `⌘W`, `⌘D`, `⌘1`–`⌘9` and the rest send your prefix and a key, so each is exactly a key conch already has — the list is on the [keys page](/docs/keys#conchs-own-window). They replace the terminal's own, which would make a tab or split of the *terminal*, outside conch. `⌘K` opens the [palette](/docs/keys#splits-and-tabs). A prefix no character stands for (`f12`) gets no shortcuts, and the file says why.
- **An application's size and title bar.** It opens at 14pt and about 160 columns by 46 rows every time, rather than restored to whatever filled the screen last, with room around the grid and between its lines. Ghostty draws a native title bar, a shade off the window (its default transparent one is the window's own background, and on macOS no setting colours it), and conch's strip along the top is drawn in that same shade, edge to edge, so the two read as one bar.
- **The left option key is alt**, for conch's alt keys and alt+click; the right one still types the characters your keyboard puts there.
- **A strip along the top**: conch's mark and the workspaces at its left (where the sidebar's top row keeps them in any other terminal), a search box in the middle that opens the palette, and on the right what is waiting or done — a click there goes to the next agent waiting. A window under 12 rows tall goes without it.
- **The title** says what is waiting — `conch · ⚑ Fix flaky tests on fix/flaky waiting` — so the title bar and the Dock's window list show it while conch is not on screen. conch sets it only in this window (it is told by `CONCH_APP_WINDOW`, which the configuration sets); in any other terminal the title belongs to whoever set the terminal up.

Your own `.local` file comes after all of this for Ghostty and kitty, so it can change any of it. foot and alacritty read their includes first, so there conch's colours hold.

It is not a window of conch's own, and will not become one: conch's interface is conch's, drawn in a terminal, and a second interface around it would compete both with that and with the terminal it is standing in for.

### doctor

```sh
conch doctor          # check what conch needs, and say how to fix what is wrong
conch doctor -json    # the same checks, for a script
```

The first thing to run when something does not work. Each line is one thing conch relies on, and anything wrong comes with the command that puts it right:

```
✓ conch     0.1.9 · darwin/arm64
✓ config    /Users/you/.config/conch/config.toml
✓ keys      ctrl+b, then 46 keys
✓ socket    /Users/you/.config/conch/conch.sock
! server    pid 28356, up 6d, on another build (0.1.8) than this conch (0.1.9)
            → conch server reload -binary /Users/you/.local/bin/conch  (panes and agents keep running)
✓ agents    claude 2.1.3 · codex 0.46.0  (not installed: gemini, opencode, devin)
✓ git       2.49.0, committing as You
! gh        2.62.0 not signed in
            → gh auth login
✓ terminal  ghostty, xterm-ghostty, 24-bit colour, says it is ghostty 1.2.0, synchronized updates
✓ machines  1 machine saved (not dialled; conch -m NAME status reaches one)

conch works; 2 things worth a look.
```

| Check | ✗ (must be fixed) | ! (worth a look) |
| --- | --- | --- |
| config | `config.toml` does not parse, so none of it is in force | an `[[actions]]` entry with no name, no command or an unknown place |
| keys | | a `[keys.bind]` entry naming something conch does not bind, or two of them on one key |
| socket | the socket path is longer than the system allows (103 bytes on macOS, 107 on Linux), so no server can listen | |
| server | the socket is there but nothing answers — stuck, or somebody else's (starting `conch` would clear it, and every pane) | not running; on another build than this `conch` (the fix reloads it onto *this* binary, or says to run the newer one when the server is ahead); missing features this `conch` uses |
| agents | the server finds none installed | not checked, because no server is running |
| git | not found | no name or email to commit as, in git's config or its environment variables; older than 2.38, which telling which branches would conflict needs |
| gh | | not found, or not signed in — pull requests, CI results and issues come through it |
| terminal | `TERM` is empty or `dumb` | no terminfo entry for `TERM` on this computer, so curses programs fall back; a terminal that names itself (Ghostty, kitty, WezTerm, foot, alacritty) while `TERM` says plain xterm, so its own keys and colours are off; no SGR mouse reports, so clicks and drags never arrive; no bracketed paste, so a pasted prompt is typed line by line into an agent; inside tmux with the same prefix as tmux (asked of tmux itself), and a key free in both to use instead |
| machines | `machines.json` cannot be read; machines are saved but there is no `ssh` | |

**It asks the terminal what it can do.** `TERM` is set by whatever started your shell and is wrong often enough to be worth checking against the terminal itself — a Ghostty whose terminfo was never installed still says it is Ghostty while `TERM` says plain xterm, and then nothing describes its keys and colours. So the command sends the terminal a few questions (`DECRQM` for the modes conch turns on, `XTVERSION` for its name, device attributes last) and reads the replies, which is the one thing it writes anywhere. It does that only when run in a terminal, never when output is redirected, and it waits 300ms at most for a terminal that will not answer. Anything the terminal says nothing about is left unsaid rather than reported as missing: a terminal that does not answer mode queries is not a terminal without the modes. Run in a conch pane it says so, because the terminal answering there is conch's own emulator and not the window you are looking at. **The TUI never asks** — a reply would land on its own input as keystrokes — so the page under `,` → **Check conch…** shows everything except what only a question can find.

It exits 1 when anything is marked ✗, and 0 otherwise. The checks run side by side, so one slow thing costs only its own wait. It changes nothing and starts nothing — not even the server — and it does not dial your machines, so a machine that is asleep cannot make it hang. Whether `gh` is signed in is asked without reaching GitHub, so an offline laptop is not called signed out (a `gh` too old for that is asked the usual way), and the token `gh` hands back is thrown away. It checks this computer: on another machine, run it there. The TUI runs the same checks a moment after it starts and shows what they find on this computer's page; `,` → **Check conch…** lists them there and checks again.

### keys

tmux's `list-keys`, for conch's prefix table. It prints one line per action — the key it answers to, the name to write in `config.toml`, and what it does:

```
—       next_layout       next layout  (space is zoom now)
```

A key you moved says what it was, one you unbound says so, and one whose key went to another action says where it went — which is the surprise worth naming, since nothing else would tell you that binding `zoom` to space took space off `next_layout`. [Rebinding](/docs/configuration#rebinding-the-keys) is `[keys.bind]` in `config.toml`; `-toml` prints the current table in that form, so you can paste it and edit from what you have rather than from a blank table.

It reads `config.toml` and nothing else — no server, no network — so it works wherever conch is installed. It exits 1 when that table has a mistake in it (an action conch does not bind, two actions on one key), naming each; `conch doctor` says the same under `keys`.

`-json` is how Conch.app takes its prefix keys: the prefix in conch's spelling (`C-a` comes out `ctrl+a`), every action with the keys it is on (an empty list for one unbound), and what was wrong with the table under `problems` — in the output rather than the exit status, so a reader still gets the keys that did resolve. A binding on the prefix itself is left out there, as the TUI leaves it out.

A digit is the tab at that place and `ctrl`/`alt`+arrow is a resize, and neither is in the table: they are a key *family*, not one action.

### bug

```sh
conch autopilot push                                        # hand the server [verify]'s autopilot policy,
                                                            # as the TUI does (Conch.app runs it)
conch bug                                                   # the facts about this conch
conch bug -open "the tree lost a terminal"                  # …in a GitHub issue, already filled in
conch bug -log                                              # where the server's log is
```

What to hand over when conch itself is the problem, without writing anything down:

```
conch 0.1.7-dev (build 29945acfb71a, darwin/arm64)
server: 0.1.7-dev (build 01096cd11ad4, darwin/arm64), pid 28356, up 6d
  reloaded 5h06m ago
panes: 25 · claude×16
machines: 2, 1 reachable
terminal: iTerm.app, xterm-256color, 247×48, icons=nerd
last error: out_of_scope: the claude agent in p1 may not reload the server
```

It is **facts, not contents**: versions, counts, sizes, the capabilities a server is missing, and conch's own last error. Never a path, a project, a branch, a pane's title or anything off a screen — which is what makes it safe to send without reading it through first. The two builds above being different is the sort of thing it is for.

`-open` opens a GitHub issue with the block already in it; nothing is sent until you press submit there. Over ssh, or anywhere with no desktop, it prints the link instead. `-log` says where the server's log is and what is in it — paths, branch names and pane titles — and leaves attaching it to you.

Run [`conch doctor`](#doctor) first: what it finds usually has a fix you can make yourself.

In the TUI the same thing is `,` → **Report a problem…**, which shows the report and offers to open the issue, copy it, or copy the log's path.

### ask

`conch ask [-y | -n] [-model] REQUEST` asks the [brain](/docs/brain); it proposes actions and runs them once you confirm. `-y` runs the plan without asking; `-n` only shows it. Requests that can only mean one thing, like _show codex_, _tell everyone to commit_ or _what is waiting?_, are [planned without the model](/docs/brain#without-the-model); `-model` asks the model anyway. `-pane ID` says which pane _this_ and _here_ mean.

`conch ask -suggest [-pane ID] [EARLIER REQUEST...]` prints, as JSON, what the Ask window offers: the agents by state, which model would plan, and what is worth asking now, each saying whether it is answered at once or planned by the model. The requests after it are earlier ones, oldest first, offered back as recent. It asks no model, so it works with none set up. [Conch.app](/docs/mac-app)'s ✦ Ask draws its list from it.

### commit-message

`conch commit-message [-context TEXT]` reads a diff on stdin and prints a commit message for it — a subject line, a blank line and a body — written by the brain set in `[brain]`; `-context` adds what the agent that made the change said it was doing. An empty diff is refused. Conch.app's **✦ Write** runs it.

```sh
git diff --cached | conch commit-message -context "adding a health check"
```

### update

`conch update [VERSION | latest | list | rollback]` replaces this binary with a release and reloads the local server onto it, keeping panes.

| Command | What it does |
| --- | --- |
| `conch update` | install the latest release, or say it is already running |
| `conch update VERSION` | install that release; an older one moves conch back |
| `conch update list` | list the releases published upstream, newest first, marking the running, latest and locally kept ones |
| `conch update rollback` | go back to the version before the last update, from the copy it kept |

See [Auto-update](/docs/installation#auto-update) and [Going back to an older version](/docs/installation#going-back-to-an-older-version).

### version

`conch version [--json]` prints the version, build and platform (also `--version`, `-v`).

### Internal commands

These are run by conch itself, not by you:

| Command | Used by |
| --- | --- |
| `conch bridge` | a remote client over ssh: connects stdio to this machine's server, starting it if needed |
| `conch report` | agent hooks and plugins, to report state to the server |
