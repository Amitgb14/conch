# Configuration

conch keeps its socket, state and settings in one directory. Most settings can be changed from the Settings screen (`,`), which writes `config.toml` for you, and every one of them from [the page it opens in your browser](/docs/interface#edit-in-browser) (`e` there, or `conch config web`).

## Files

Everything lives in `~/.config/conch`. Set `CONCH_HOME` to use another directory; without it, conch uses `$XDG_CONFIG_HOME/conch` when `XDG_CONFIG_HOME` is set.

| File | Contents |
| --- | --- |
| `conch.sock` | the server's socket (override with `CONCH_SOCKET`) |
| `server.log` | the server's log |
| `projects.json` | the projects in the sidebar |
| `claude-settings.json` | the hooks conch passes to Claude Code with `--settings` |
| `ui.json` | fold state, sidebar width, tabs and splits, saved ssh hosts |
| `machines.json` | remote machines: only an ID, label and ssh target |
| `phone.json` | the phones paired with [`conch web`](/docs/phone): a name, a permission and a hash of each one's token, their push subscriptions, and the key pushes are signed with |
| `ssh/config` | generated ssh config |
| `binaries/<os>-<arch>/conch` | conch builds for other platforms |
| `agents/claude.toml` | optional override of Claude's [screen rules](/docs/agents#how-the-state-is-decided) |
| `config.toml` | your settings |
| `themes/NAME.toml` | [themes of your own](#themes-of-your-own), one a file |
| `scenes/NAME.toml` | Conch.app's [scenes of your own](#scenes-of-your-own), one a file, with any pictures beside them |

## Environment variables

| Variable | Effect |
| --- | --- |
| `CONCH_HOME` | the directory above |
| `CONCH_SOCKET` | the server socket path |
| `CONCH_SOURCE` | conch's source tree, for cross-compiling to [remote machines](/docs/remote-machines#adding-a-machine) |
| `CONCH_REMOTE_BINARY` | a prebuilt conch binary to install on remote machines |
| `CONCH_VERSION`, `CONCH_INSTALL_DIR` | release and directory for the [install script](/docs/installation#install-script) |
| `DAYTONA_API_KEY`, `BOAT_API_KEY`, `TENSORLAKE_API_KEY` | the key for [sandboxes](/docs/sandboxes), one per provider: the variable each provider's file names |
| `DAYTONA_API_URL`, `DAYTONA_TARGET` | Daytona's API (a self-hosted one) and region, when `[sandbox.daytona]` doesn't set `api_url` and `region` |
| `BOAT_API_URL` | boat.dev's API, when `[sandbox.boat]` doesn't set `api_url` |
| `TENSORLAKE_API_URL`, `TENSORLAKE_SSH_HOST` | Tensorlake's API, when `[sandbox.tensorlake]` doesn't set `api_url`, and its ssh gateway in place of the file's |
| `CONCH_PROVIDERS_URL` | the [provider registry](/docs/sandboxes#the-provider-registry) conch installs from (`https://amitgb14.github.io/conch-integrations`, one index for sandbox providers and every other integration): its `index.json` (and `index.json.sig`, checked when `CONCH_PROVIDERS_KEY` gives the key) and the files it lists. https, or http on this computer |
| `CONCH_LOG_CALLER` | `1` writes a line per connection saying which pane the server placed it in, with the process ancestry it climbed — for finding out why an agent that should be [scoped](/docs/agents-together#what-an-agent-may-do) is not |
| `CONCH_STATUS` | `0` stops conch [telling the terminal what its agents are doing](/docs/agents#conch-reports-its-own-state-too), `1` makes it do so where it otherwise would not |

## config.toml

A `config.toml` conch cannot read never keeps you out: it starts on the defaults and says what was wrong with the file, in the TUI as a message on start-up and on the terminal for `conch ask`. Saving from the Settings screen then keeps the file that could not be read as `config.toml.invalid`, so a half-finished edit is never written over.

All keys with their defaults:

[git]

stale_days = 30    # conch branch prune and the Mac app's Old branches call a branch with no commit for this long old

[verify]

                 # empty keeps the app on theme (the TUI always uses theme)
accent = ""      # override: teal, blue, green, orange, pink, red, gray, purple or "#rrggbb";
                 # the TUI and Conch.app both draw selections and focus in it
cost = true      # show what agents spend in the tree, Sessions and the pages

[shell]

### Rebinding the keys

`[keys] prefix` is the key that hands control back to conch from a pane. `[keys.bind]` is what the keys **after** it do, the way tmux's `bind-key` is: the name of what the key does, and the key to put it on.

```toml
[keys]
prefix = "ctrl+a"      # like tmux's set -g prefix C-a

[keys.bind]
split_right = "\\"      # ctrl+a \  splits right, instead of v % |
split_down = "-"
next_tab = "C-n"       # tmux's spelling is taken too: ctrl+n
prev_tab = "C-p"
zoom = "f"
close_split = ""       # unbound: nothing closes a split from a pane
```

The rules are tmux's:

- **What you do not name keeps its default.** The table is a change to the keys, not a replacement for them.
- **A key you name is taken off whatever had it.** Binding `zoom = " "` moves zoom onto space and leaves `next_layout` with no key — `conch keys` says so in as many words, rather than leaving you to find it.
- **An empty key unbinds the action**, as `unbind-key` does. Nothing is unreachable that way: the prefix is not an action, and the menus, the status bar and the help overlay stop offering a key once it has none.
- **Two actions on one key is a mistake, not a race.** The first by name keeps the key, the other is reported by `conch keys` and `conch doctor`, and the same file always gives the same keys.

Keys are written in conch's own notation — `ctrl+n`, `alt+x`, `f`, `space`, `up` — and tmux's is understood as well (`C-n`, `M-x`, `Space`). Case matters for letters, because `s` and `S` are two keys.

**`conch keys` lists every name**, what it does and what it is on now; `conch keys -toml` prints the whole table ready to paste. The help overlay (`?`) and everything conch says about a key — menu labels, the status bar, hints — read from the same table, so they show your keys and not the defaults.

Two keys are not in the table, because neither is one action: a **digit** is the tab at that place, and **`ctrl`/`alt`+arrow** is a resize in a direction. The keys in the tree (`t`, `c`, `n`, `a`, `M`, `H`…) are not either — the table is the prefix table, as tmux's is.

### notify

`quiet_start` and `quiet_end` (`"HH:MM"`) silence alerts every day between them; the range may wrap past midnight. Waiting agents still show in the sidebar. Leave either empty for no quiet hours.

`command` sends every alert somewhere else as well, by running it in `sh` with the alert on stdin as JSON — `{"title": …, "body": …, "at": …}` — and in `CONCH_NOTIFY_TITLE` and `CONCH_NOTIFY_BODY`. conch holds no service's token; the command does:

```toml
command = "curl -s -d \"$CONCH_NOTIFY_TITLE: $CONCH_NOTIFY_BODY\" ntfy.sh/my-conch-alerts"
command = "jq -c '{text: (.title + \": \" + .body)}' | curl -s -H 'Content-Type: application/json' -d @- \"$SLACK_WEBHOOK_URL\""
command = "curl -s \"https://api.telegram.org/bot$TG_TOKEN/sendMessage\" -d chat_id=$TG_CHAT --data-urlencode text=\"$CONCH_NOTIFY_TITLE: $CONCH_NOTIFY_BODY\""
```

It runs where conch's TUI runs, follows `enabled` and quiet hours like the other alerts, and is stopped after 30 seconds if it hangs.

Slack, Discord and ntfy also come as [notify integrations](/docs/integrations#notifications), sent by conch's server rather than the TUI, with the webhook's address kept like a key; they follow `enabled`, `waiting` and `done`, not quiet hours.

`silence` is how long a pane watched with `ctrl+b M` must go without output before it alerts; see [Watching a pane](/docs/interface#watching-a-pane). Less than 1 means the default, 30.

`limits` alerts when Claude's 5-hour or weekly window, Codex's windows or a spend limit passes a percentage in `limit_at` (1–100). Each threshold alerts once per window and machine, even across restarts of the TUI; a new window after a reset alerts again.

### ui

`mouse = false` leaves the mouse to your terminal entirely. With it on, hold shift (option in iTerm2) to select text with the terminal instead.

### agents

`claude_idle_compaction = false` stops Claude Code compacting a conversation left idle before its prompt cache expires ("Compacted while idle…"), in the Claude panes conch starts, from each one's next start. It is **Compact Claude while idle** under Agents in Settings, the settings page's and Conch.app's. conch writes it into the settings file it starts Claude with and never `~/.claude/settings.json`, which a Claude started outside conch still reads. Unset is Claude's own default.

`antigravity_api_key_env = "NAME"` starts Antigravity CLI with the Gemini API key in the variable `NAME` instead of your Google sign-in. conch keeps no key: it starts `agy` with `GEMINI_API_KEY="$NAME"`, which your login shell fills in from your profile, and with `--settings '{"modelProvider":"gemini"}'`, which lasts for that launch and is never written to agy's `settings.json`. If `NAME` is empty when an agent starts, the pane says so and stops. It is **Antigravity CLI: variable holding a Gemini API key** under Agents in Settings.

### brain

The model behind `:` and agent summaries. `[brain]` also takes `base_url`, `api_key_env`, `command` and `no_fast_path` (send every request to the model, even [those conch plans alone](/docs/brain#without-the-model)); see [Brain](/docs/brain#configuration).

### update

`check_releases` asks GitHub once a day whether a newer release exists (release builds only). `auto = true` installs what that check finds without waiting for **u**, and reloads the local server onto it; it needs `check_releases`. `conch update rollback` goes back. See [Auto-update](/docs/installation#auto-update).

### remote

`upload_drops` uploads local files dropped (pasted as paths) on a remote machine's pane to that machine and pastes their paths there; `false` pastes the local paths unchanged. `upload_max_mb` is the largest file uploaded. See [Dropping files on a remote pane](/docs/remote-machines#dropping-files-on-a-remote-pane).

### sandbox

`[sandbox.<provider>]` sets up [sandboxes](/docs/sandboxes), one table per installed provider; the Settings screen has them under **Sandboxes** (`,` then `5`), which lists the providers and opens one. Each provider's file says which of `region`, `image`, `size` or `cpu`/`memory`/`disk` it takes, and which values (`conch sandbox -provider P settings`); a value it does not offer is refused before anything is made. `target` and `snapshot`, which older conches wrote, are read as `region` and `image` when those are empty. A table for a provider this build doesn't know is left alone rather than dropped when the settings are saved. `api_key` keeps the key in this file (0600) and wins over `api_key_env`; leave it empty to read the key from your environment every time, which is what conch does otherwise. The key itself is never stored: `api_key_env` only names the variable it is read from. `auto_stop` other than 0 lets Daytona stop a sandbox that long after the last ssh connection or API call — agents working inside don't count, so they stop too. `env` names variables passed into every sandbox `conch sandbox create` makes, on top of its `-env` flags; the provider keeps their values with the sandbox.

boat.dev's machines come in named sizes (`small`, `default`, `large`); a size name in `snapshot`, as older conches kept it, is still a size. It has no idle timer of its own, so `auto_stop` is how long a new sandbox is *given*, counted from when it was made: 120 minutes by default, what boat.dev's free trial allows, and **Life** in its settings page. Raise it on a paid plan. conch's own `idle_stop` is what stops a sandbox nobody is using, and normally gets there first.

<Callout type="note">

The Settings screen rewrites `config.toml`, so comments in a hand-edited file are not preserved.

</Callout>

## Themes of your own

A file in `~/.config/conch/themes/`, named for the theme (`dusk.toml` is `theme = "dusk"`), starts from a built-in theme and sets only the colours you want changed. The TUI, the settings page and Conch.app all read the same files: the theme is in their lists after the built-in ones (in the app, **View → Theme → Your Themes**, which also has **Open Themes Folder**), and it colours the terminals in the panes too.

```toml
# ~/.config/conch/themes/dusk.toml
name = "Dusk"                    # what the lists call it; the file's name if left out
based_on = "vscode-dark-modern"  # any built-in theme; conch's own if left out
bg = "#16161e"                   # the window and the terminals' background
fg = "#c0caf5"                   # text
accent = "#7aa2f7"               # selection, focused borders
sel_fg = "#ffffff"               # text on the accent
border = "#29293a"
muted = "#565f89"                # secondary text
ok = "#9ece6a"                   # done, added lines, passing checks
warn = "#e0af68"                 # waiting, warnings
err = "#f7768e"                  # failures, removed lines
work = "#7dcfff"                 # working agents, hashes
sel_dim = "#292e42"              # the selection while focus is elsewhere
merged = "#bb9af7"               # merged pull requests
light = false                    # Conch.app's: draw it as a light window (else decided by bg)
```

Colours are `#rrggbb`. A file that does not read, a colour written any other way, a key that is not one of these, a `based_on` that is no built-in theme, or a file named like a built-in theme is left out, and said where the themes are listed (the TUI's **Colours**, the app's **Your Themes**). A new or changed file is read the next time those lists open. `[ui] accent` still goes over whichever theme is in use.

## Scenes of your own

Conch.app draws a scene of your own behind its window the way it draws its own: a file in `~/.config/conch/scenes/`, named for the scene (`bay.toml` is `background = "bay"`). The file only describes a scene — colours, a picture, which pieces move — and runs nothing, so a scene somebody hands you can do nothing but look like something. It is offered after the built-in scenes in **Settings → Mac App → Background**, which also has **Open Scenes Folder**.

```toml
# ~/.config/conch/scenes/bay.toml
name = "The bay"                     # what Settings calls it; the file's name if left out
sky = "#FFB37A #F07A5A #5A3A6A"      # by day, top to bottom: 1 to 4 colours in one string
night_sky = "#1A1030 #0A0818"        # under a dark theme; the day's if left out
ground = "#2A1A2A"                   # a band along the bottom; none if left out
night_ground = "#0A0A10"
image = "bay.jpg"                    # a picture beside this file, filling the window
night_image = "bay-night.jpg"
pieces = "snow"                      # "bubbles", "snow" or "stars"; none if left out
count = 60                           # how many, 1 to 200
```

A scene needs a `sky` or an `image`. A picture is a png, jpg, heic, tiff, gif or webp file in the scenes folder itself, named alone (no path), of 25 MB at most. A file that does not read, a key that is not one of these, or a file named like a built-in scene is left out, and said under the scenes in Settings. A new or changed file, or picture, is read within a second.

## `[web]`

The phone gateway, [`conch web`](/docs/phone). Set from **Settings → Web** in the TUI.

| Key | Default | Meaning |
| --- | --- | --- |
| `url` | none | the address phones open: the `https://…ts.net` name `tailscale serve` gives. With it, `conch web` listens on loopback behind Tailscale, and the pairing QR code points here |
| `port` | `8722` | where `conch web` listens |
| `relay` | none | a [relay](/docs/phone#through-a-relay) `conch web` connects out to, so a phone reaches this computer from any network: `wss://relay.example.com`, a server running `conch relay`. Everything through it is encrypted between the phone and this computer, but it serves the phone's app, so use one of your own |

`-url`, `-port` and `-relay` given to `conch web` win over these.

## `[app]`

How the [Mac app](/docs/mac-app) draws its window — **Settings → Mac App**, or the settings page. The TUI keeps its own tab bar and colours.

| Key | Default | Meaning |
| --- | --- | --- |
| `tabs` | `""` | where the tabs go: `""` above the panes, `"left"` in the sidebar above the tree, grouped under each machine, `"right"` in a column of their own |
| `density` | `""` | `"compact"`: a pane's header shrinks, the gaps between splits close up and the toolbar is shorter |
| `sidebar` | `""` | `"glass"`: the desktop shows through the sidebar, as Finder's does. Panes stay solid |

The toolbar, sidebar, tabs and status bar are frosted over it. Chosen in **Settings → Mac App → Background** |
| `background_through` | `0` | how much of the scene shows through a pane, in percent, 0 to 60; `0` keeps terminals solid |

| `background_fireworks` | `true` | fireworks over the scene for a moment when one of the window's pull requests merges, and a note saying which; only the note under Reduce Motion |
| `[app.project_backgrounds]` | none | a project's own scene, by name: `conch = "pines"`, or `"none"`. Its window shows it, and so does any window while one of its tabs is in front |
| `ports` | `true` | the TCP ports a pane's programs listen on, in its header — a click opens one in the browser, or on another machine copies the ssh tunnel to it |
| `scratch_key` | `false` | option-space shows the scratch layer from anywhere, Conch.app in the background or not, as Ghostty's quick terminal does; off, it works in the window only |
| `prefix_keys` | `true` | `[keys] prefix` and the keys after it work in the app's panes as in the TUI, from the same table; off, the prefix goes to the program |
| `check_updates` | `true` | Conch.app asks GitHub once a day whether a newer release of itself is out and says so in the status bar; **Conch → Check for Updates…** asks now. `[update]` is the command line's. A build from source never asks |
| `auto_update` | `false` | install that release as soon as the check finds one — downloaded, verified (checksum, signature, Team ID, notarization) and put in place of the app — to run from the next launch; off, the app asks first |
| `text_size` | `100` | the window's own text — the sidebar, tabs, the git tab, the status bar — in percent, 80 to 160; **View → Bigger / Smaller Window Text** (⇧⌘+ / ⇧⌘−) steps it through 80, 90, 100, 110, 125, 140, 160 and ⌃⇧⌘0 puts it back, writing it here. The sidebar widens with it |
| `icons` | `""` | the icons beside each section of Settings and each row of the window's sidebar (machines, workspace, projects, branches, terminals, Sessions and Files; agents keep their own marks): `""` Lucide's outlines, or the Mac's own SF Symbols, `"sf"` in line or `"sf-fill"` filled. Chosen in **Settings → Appearance → Icons**, from a card of each set's icons: the pointer on one shows it in the sidebar, a click chooses it |

**Conch.app's own updates.** A release found is said in the status bar and a notification, with **Install**, **Later** and **Skip This Version** and its release notes. Install downloads `Conch_<version>_macos_arm64.zip`, checks it against its `.sha256`, checks the app inside (`codesign --verify --deep --strict`, the same Team ID as the running app, and Gatekeeper taking it as notarized), puts it in place of the app and relaunches; the first launch then offers **Reload Server**, which moves the server onto the app's conch, keeping panes and agents. The app it replaced is kept for one update: **Conch → Roll Back Update** puts it back. An app run from its disk image, a temporary copy macOS made (App Translocation) or a folder you can't write (installed by an admin) is refused, saying why. The same runs from a shell: `conch app update check | install VERSION | rollback`.

## `[trackers]`

Where [`conch task -ticket`](/docs/tasks#tasks) and `conch ticket` find tickets besides GitHub issues: Linear, and Jira Cloud. The server on the project's machine reads them, so set this up there. Set from **Settings → Trackers** on the settings page.

| Key | Default | Meaning |
| --- | --- | --- |
| `linear.api_key_env` | `LINEAR_API_KEY` | the variable holding a Linear personal API key (Linear → Settings → Security & access). Not in the environment, the Mac's Keychain is read: a `conch-mcp` item with the variable's name as its account |
| `linear.api_key` | none | the key itself, kept in this file as it is |
| `linear.team` | none | the team key whose tickets `conch ticket ls` lists |
| `linear.api_url` | Linear's | another GraphQL endpoint |
| `jira.url`, `jira.email` | none | your Jira Cloud site and your Atlassian account's email |
| `jira.api_token_env` | `JIRA_API_TOKEN` | the variable holding an API token (id.atlassian.com → Security → API tokens), read as Linear's is |
| `jira.api_token` | none | the token itself |
| `jira.project` | none | the project key whose tickets are listed |

With both set up, say which tracker a project uses — Linear's and Jira's keys look alike — or name it in the ticket (`linear:ENG-123`):

```toml
[[trackers.projects]]
project = "api"        # a conch project, by name or path
tracker = "linear"
key = "ENG"            # its team (Linear) or project (Jira); "" is the default above
```

conch never moves or comments on a ticket by itself: `conch ticket` does, when you (or an agent you asked) run it. OAuth sign-in is not supported yet; a personal key is.

## `[[teams]]`

Agents grouped by what they work on — backend, UI, a report — so a project with a dozen agents reads as a few teams. In [Conch.app](/docs/mac-app) a project's **Agents** splits into a row per team, each with its count, then **No team**; a project where nobody is in a team keeps its single list.

```toml
[[teams]]
name = "Backend"
color = "blue"
projects = ["api", "worker"]
branches = ["conch/cloud-*"]

[[teams]]
name = "UI"
branches = ["ui/*", "*-redesign"]
```

A new agent joins the first team whose rule matches its project's name or its branch (`*` matches anything, slashes too). One put in a team by hand stays there whatever the rules say: right-click an agent → **Team**, drag it onto a team's row, pick one in **New Task** (⌘N), or from a shell `conch agent team p3 UI` (`-` for no team, `-clear` back to the rules) and `conch task -team UI`. A team's row has an agent button, the bot icon as a project's row has, and **Start an Agent in This Team** on its menu: the agent chosen starts in the project's folder and joins the team (agents only — a terminal is in no team). It also has **Show Side by Side**, its agents in one tab, and **Broadcast to This Team…**; `conch status -team UI` lists its agents. **Rename Team…** renames it everywhere — its entry here and every agent put in it by hand — and **Delete Team…** removes it: a team with agents asks whether to close them, move them to **No team**, or cancel. **Settings → Teams** edits these — a team's colour as a row of dots: **Auto** (by its place), the nine colours, and one of your own from the colour panel, saved as `#rrggbb` — and lists too the teams made from an agent's menu that are not here yet, so every team in use is on it; **Give It a Colour and Rules** adds one here with its name, and its agents stay in it. Each team there shows its agents as one mark per agent with how many are open, and a spinner round the mark while any of them is working (`4 · 1 working`). A team set by hand lives on the pane and survives a server reload; it needs a server with `pane.team.v1`. In Conch.app, putting an agent in a team (**New Team…**, the Team menu, a drag) also adds that team here by name, so it stays when its agents close; a team here with nobody in a project yet still has a row under that project's Agents — unless its `projects` name others — so an agent can be started in it.

| Key | Default | Meaning |
| --- | --- | --- |
| `name` | — | the team's name |
| `color` | by its place | `blue`, `orange`, `purple`, `teal`, `green`, `red`, `pink`, `yellow`, `gray`, or `#rrggbb` |
| `projects` | none | project names, any case, whose agents join it |
| `branches` | none | branch patterns, `*` for anything: `ui/*`, `*-redesign` |

## `[[actions]]`

Commands of your own on conch's menus. Most of what a plugin system gets asked for is this: run the project's tests on this branch, open a pull request, tail a log, open the worktree in something else. Each is already a shell command somebody runs by hand in that checkout — conch's part is knowing *which* checkout.

```toml
[[actions]]
name = "Run tests"
run  = "go test ./..."
on   = ["branch", "project"]

[[actions]]
name = "Open a pull request"
run  = "gh pr create --fill"
on   = ["branch"]

[[actions]]
name = "Open the folder"
run  = "open ."        # xdg-open on Linux
keep = false
```

An action is then on the menu of a matching row — **m**, or right-click — under **Actions…**, numbered, and it runs in a terminal of its own on that row's machine, in that row's directory.

| Key | Default | Meaning |
| --- | --- | --- |
| `name` | — | the label on the menu, and what its terminal is called |
| `run` | — | the command, read by `sh -lc`: a pipeline, several commands, a script of yours |
| `on` | all four | the rows it is offered on: `pane`, `branch`, `project`, `machine` — and the events it runs on, which make it a [hook](#hooks) |
| `keep` | `true` | leave the terminal open when the command exits, so what it printed can still be read. `false` closes it like any other terminal |
| `timeout` | `300` | a hook's limit in seconds: a run still going then is stopped, with everything it started. Menus ignore it |

The command is given conch's own variables, so one action works from any row. What a row has nothing to say about is empty rather than missing, which a `set -u` script survives:

| Variable | What it holds |
| --- | --- |
| `CONCH_MACHINE` | the machine the row belongs to, as `conch -m` names it |
| `CONCH_PROJECT` | the project's name |
| `CONCH_BRANCH` | the branch, where the row has one |
| `CONCH_WORKTREE` | the directory it runs in, which is also its working directory |
| `CONCH_PANE` | the pane the action was started from, on a pane's row |

`CONCH_SOCKET` is in every pane's environment already, so an action can drive conch itself: `conch send`, `conch new`, `conch task`.

**Where it runs.** On the machine the row belongs to — a remote machine's action runs over there, in that checkout, not on the computer the TUI is on. A branch nobody has checked out has no directory to run in, and conch says so rather than making a worktree behind your back: open a terminal on it first (**n**).

**Settings → Actions** (`,` then `7`) lists what is configured, which actions are hooks and on what, and names any problem: an action with no name or no command, two with the same name, an `on` that is neither one of the four rows nor one of the events below.

### Hooks

An action whose `on` names an **event** is run by conch's server when that event happens, rather than chosen from a menu. It runs with no TUI open, and never in the way of the event that fired it.

```toml
[[actions]]
name = "Set up the worktree"
run  = "make setup"
on   = ["worktree.created"]
timeout = 600

[[actions]]
name = "Tell the channel"
run  = 'curl -sd "$CONCH_BRANCH: $CONCH_EVENT" "$SLACK_HOOK"'
on   = ["agent.done", "pr.merged"]
```

| Event | When |
| --- | --- |
| `worktree.created` | conch made a worktree: a task, `conch worktree add` and the tree's new branch, a group task, a branch moved here |
| `agent.done` | an agent finished a turn |
| `agent.waiting` | an agent is waiting on you: a permission, a question |
| `pr.opened` | a pull request was opened, or reopened, on one of the project's branches |
| `pr.merged` | a pull request conch had seen open was merged |
| `task.failed` | a task could not be started — from `conch task`, the schedule, or intake |

Each event fires its hooks once. A server that restarts or reloads does not fire them again: an agent a reload takes over comes back with no earlier state, which is no change, and the pull requests conch last saw are kept in `hooks.json`. A pull request already open, or already merged, when conch first reads a project is not news. Neither is one opened and merged between two reads, which can't be told from one merged long ago.

A hook runs `sh -lc` in the event's worktree, else the project's folder, else your home, with these set (empty when the event has nothing to say):

| Variable | What it holds |
| --- | --- |
| `CONCH_EVENT` | the event's name |
| `CONCH_ACTION` | the action's name |
| `CONCH_PROJECT`, `CONCH_PROJECT_ID`, `CONCH_ROOT` | the project's name, id and folder |
| `CONCH_BRANCH`, `CONCH_WORKTREE` | the branch and its checkout |
| `CONCH_PANE`, `CONCH_AGENT`, `CONCH_MESSAGE` | the agent's pane, which agent it is, and what it last said (`agent.*`) |
| `CONCH_PR`, `CONCH_PR_URL`, `CONCH_PR_TITLE` | the pull request (`pr.*`) |
| `CONCH_ERROR` | why a task could not start (`task.failed`) |
| `CONCH_SOCKET` | the server's socket, so a hook can drive conch |

The pane is `CONCH_PANE`, as for an action from a menu, never `CONCH_PANE_ID`: that one tells conch's own commands they run *inside* the pane, and an agent's report sent from a hook would land on the agent.

Each run is a job of its own. Two events at once run side by side, and a run is stopped at its `timeout` (five minutes when the action does not say), with everything it started. Its output goes to `hooks/logs/` beside `config.toml`, the first megabyte of it, with how much more was cut said at the end. The newest 200 logs are kept. A run that fails or is stopped at its timeout is said in the **activity feed**, where the autopilot's notes are, with its log's path. A hook taken out of `config.toml` while it runs finishes as it was, and the next event does not run it. Stopping or reloading the server stops the runs under way, and their logs say so.

An action that names only events is a hook alone and on no menu. Name a row as well (`on = ["agent.done", "branch"]`) to have it in both places. An action that names no event is never run on one, so a `config.toml` written before hooks does just what it did.

Hooks can also be shared: an integration of kind `hook` is installed from a registry like any other ([more](/docs/integrations#hooks)), and runs after your own.

<Callout type="note">

An action is arbitrary command execution, from your own file. Nothing runs until you choose it from a menu, or until an event it names happens. conch fetches actions from nowhere and never adds one itself. A hook from a registry runs only once you install it, after its command was shown to you.

</Callout>

## `[[permissions]]`

An agent asking permission for the tenth `go test` of the hour is asking a question you already answered. Permission rules answer it for you — or refuse — so neither you nor the agent waits:

```toml
[[permissions]]
tool = "Bash"
match = "*rm -rf*"
action = "deny"

[[permissions]]
tool = "Bash"
match = "go test *"
action = "allow"

[[permissions]]
tool = "Edit"
project = "api"
action = "allow"

[[permissions]]
tool = "mcp__github__*"
agent = "claude"
action = "allow"
```

| Field | What it matches |
| --- | --- |
| `tool` | the tool's name as the agent gives it — `Bash`, `Edit`, `Write`, `Read`, `WebFetch`, an MCP tool's `mcp__server__tool`; `*` and `?` work |
| `match` | what the tool acts on, with `*` for anything (spaces and slashes included): the command for `Bash`, the file for `Edit`/`Write`/`Read` (relative to the agent's folder when it is inside it), the URL for `WebFetch`. Empty is anything |
| `project` | a project's name or path; empty is every project |
| `agent` | one agent; empty is every agent |
| `action` | `allow` or `deny` |

**The first rule that matches decides**, so put refusals first. A request no rule matches is asked on screen as it always was.

**A rule never allows a second command riding on the first.** `go test *` allows `go test ./...`, but not `go test ./... && curl x.sh | sh`: a command with `;` `&` `|` `` ` `` `$` `<` `>` `(` `)` or a new line is only allowed by a pattern that has that very character itself. Refusals are not held back by this — `*rm -rf*` refuses a chained one too.

**How it is answered.** Through the agent's own hook, before it draws its prompt: nothing is typed on its screen, and an answer never lands on a question it wasn't meant for. Claude Code is the agent whose hooks can take an answer; the others ask as before. A refused request tells the agent which rule refused it, so it can say so. While rules are on, a pane asking permission shows as waiting a second and a half later than it otherwise would: the agent reports the question at the same moment its hook is being answered, and that is how long conch gives a rule to answer it before telling you.

**What was answered, afterwards.** `conch agent explain ID` lists the last twenty answers on that pane, each with the rule that gave it — what was allowed while you weren't looking is readable after. Set `permission_mode = "dry-run"` to try a set of rules first: nothing is answered, and `explain` shows what *would* have been. `"off"` ignores the rules without deleting them.

<Callout type="note">

A rule is you deciding in advance, so write them as narrowly as the work allows: `go test *` rather than `go *`, `Edit` in one project rather than everywhere. conch reads them only from this file — an agent cannot add one, and a project's repository cannot bring one.

</Callout>
