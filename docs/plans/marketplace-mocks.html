Integrations for conch — mocks

One place to browse and install what conch talks to: code hosts, CI, ticket trackers, sandboxes, notifications. Each integration is a provider file — a description, never code — from a registry anyone can add to, checked by a hash, holding your key in the Keychain. Built-ins (GitHub, GitHub Actions, Linear, Jira) are listed the same way so there is one model. Conch.app first; the TUI and CLI get the same data.

9 · What an integration is: a provider file

Same shape as today's sandbox files: calls, where the answer is in the reply, a contract per kind. conch's code owns what is done with the answers; the file only says where they are.

kind = "ci"                 # the contract it fills
name = "circleci"
label = "CircleCI"
format = 1
api = "https://circleci.com/api/v2"
auth_header = "Circle-Token"
auth_value = "{key}"
key_env = "CIRCLECI_TOKEN"
docs = "https://circleci.com/docs/api/v2"

[detect]                     # suggests it for a project
files = [".circleci/config.yml"]
checks = ["ci/circleci*"]      # a check's name or link

[project]                    # the remote → the project slug
slug = "gh/{owner}/{repo}"
[runs]                       # runs of a branch, newest first
call = "GET /project/{slug}/pipeline?branch={branch}"
items = "items"
id = "id";  commit = "vcs.revision"
url = "https://app.circleci.com/pipelines/{slug}/{reply.number}"

[failed_log]                 # a failed run → its output, in steps
steps = [
  { call = "GET /pipeline/{id}/workflow", pick = "items[status=failed]" },
  { call = "GET /workflow/{reply.id}/job", pick = "items[status=failed]" },
  # no log in v2: v1.1's build, then each failed step's output_url
  { call = "GET /api/v1.1/project/{slug}/{reply.job_number}",
    follow = "steps[*].actions[status=failed].output_url", text = "[*].message" },
]

[rerun]
call = "POST /workflow/{workflow}/rerun"
body = { from_failed = true }

[states]                     # theirs → conch's pass fail pending
success = "pass"; failed = "fail"; running = "pending"

Illustrative. CircleCI's v2 API has no job log; the log comes from v1.1's build and each failed step's presigned output_url (which CircleCI calls unsupported), hence follow — a built-in operation, not a script. The presigned host is outside api, so it is listed and fetched without the key. A code host's contract (pull requests, checks, merge, comments) is far larger than CI's, which is why the plan puts GitLab and Bitbucket last and lets them be backed by their CLI (glab) where that is cheaper and safer than a data file.
